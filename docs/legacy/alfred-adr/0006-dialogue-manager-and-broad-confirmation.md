# 0006. Dialogue manager and broad confirmation

Status: accepted (owner decision, 2026-11-18, after a live failure). Amends ADR 0002 and 0004 (the exact word `evet`). Ported in spirit from the Acme dialogue manager; Alfred shares no code with it.

## Context
The owner confirmed an import preview with "onayliyorum", then "evet". Only the exact word "evet" was accepted, so "onayliyorum" went to the language model, came back `unclear`, and any unrecognised text closed the pending action as `superseded`; the next "evet" answered "no pending action". An unrecognised message destroyed the preview.

## Decisions
1. **Broad confirmation, deterministic** (`dialogue.parse_confirm`, vocabulary in `i18n.py`). The WHOLE message, normalised (case, punctuation, dotless i, repeated letters, Whisper output, thumbs-up emoji), must be an affirmation (evet, tamam, olur, onaylıyorum, kaydet, ekle, ok, doğru, yap, tabii, peki, ...) or a negation (hayır, yok, vazgeç, iptal, istemiyorum, dur, ...). Extra content is never a confirmation: "evet ama saati 16:00 yap" is an EDIT. Without a pending preview only the exact old words keep their old meaning.
2. **Deletes stay strict.** On a delete preview a plain yes ("evet", "tamam", thumbs-up) is refused with the `evet sil` hint; "evet sil", "sil" and an explicit approval ("onaylıyorum") delete.
3. **A pending preview is never closed by an unrecognised message.** Only an explicit cancel, a confirmation, TTL expiry (10 minutes, or the import TTL), an applied edit (a new pending action; the old one is superseded atomically in the same transaction), or a new write request the owner agrees to park ("Önceki önizleme iptal edilsin mi?") closes it. Anything else is answered (read, chit-chat, "emin misin") and the preview is re-offered: "Önizleme hâlâ onayınızı bekliyor (evet / hayır)".
4. **One model call per message while a preview is pending** (when NL is on, consent given, under the daily cap). The input is DATA: the draft (numbered events), today, the last bot question, the last 8 log turns and the upcoming events. The output is strict JSON operations: `set_field`/`apply_to_all` (title, date, time, duration_min, reminder_min, location, notes), `remove_item`, `add_items`, `shift_dates`, `read_query` (today, tomorrow, week, birthdays, upcoming), `cancel`, `chitchat`, `new_request`. `dialogue.validate_ops` rejects anything else; dates and times must be ones the owner said in that message; item numbers must exist. `dialogue.apply_ops` applies them to a copy of the draft in code and the preview is re-rendered by code. A model `confirm` is not an operation: only the deterministic parser confirms, so "change and save" shows the new preview first.
5. **Rules fallback** (model off, over the cap, failed, or schema error): reads via `rules.parse`, and plain slot edits ("saati 16:00 yap", "yarın olsun", "hepsini bir gün ertele", "1 saat önce hatırlat") via `dialogue.rules_ops`. With several events an edit needs a target ("hepsi"); otherwise the preview is kept and re-offered. Only add previews are editable; for edit and delete previews the model may only read, cancel, chat or park.
6. **Facts are never re-asked.** Known fields live in the draft; a question is asked only for what is missing and a repeated question is reworded (`i18n.ask`).
7. **Debounce** (`bot.group_updates`, `Bot.settle`): plain texts of the owner within 4 seconds of each other are merged into one turn (joined by a newline) after at most two short extra polls. Confirm, cancel, commands, voice and callbacks never merge.
8. Everything stays preview-gated: operations only change a stored draft; a write still needs the confirmation of the code-rendered preview (ADR 0002).

## Consequences
One extra model call per message while a preview is open (counted against the daily cap). Edits renew nothing but keep the original TTL span. Known limits: no operations on edit/delete previews; an unclear edit on several events asks for a target by re-offering only.
